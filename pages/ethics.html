Ethics and privacy

How this application handles personal information, and where its limits are.

Data minimisation

The application only asks for what a task list actually needs: a title, a course, a due date, a description and optional notes. It deliberately does not ask for a student number, an address, a date of birth or any health information. Personal information that is never collected cannot be leaked, so the safest design decision was to leave those fields out.

Where the data is stored

Tasks are written to the browser's localStorage under the key studyTaskManager.tasks. Nothing is sent to a server, because there is no backend and no network request in the application. This means the data stays on the device the student is using, and it is not shared with the university or any third party.

There are no analytics scripts, advertising trackers or third party fonts on any page, so visiting the site does not create a profile of the user.

Access control

The task list is hidden until the user signs in, which demonstrates how a login gate protects a page. The implementation is honest about its limits: the account is hard coded in js/tasks.js and the password is compared in the browser, so it is a demonstration of the concept rather than real security. Anyone who opens the developer tools could read the stored tasks.

In a real product this would need a server side login, hashed passwords, an expiring session and HTTPS. Showing the honest limitation matters more than pretending the demo is secure.

Input validation as a privacy control

Before a task is saved, the form rejects empty required fields, dates that do not exist and due dates in the past. Validation is usually described as a way to stop bad data, but it also reduces risk: it keeps unexpected values out of the stored list and forces every task to have a known shape, which makes the data easier to audit and delete.

User supplied text is escaped before it is inserted into the table, so typing HTML or a script into the description field is displayed as text instead of being executed.

Deleting data

Deleting a task asks for confirmation first, then removes the record from storage immediately. There is no hidden archive and no soft delete, so the user can actually get rid of information instead of simply hiding it from view.

If this became a real product

  • Move storage server side with encrypted connections and a proper session.
  • Store only hashed passwords and never log them.
  • Let the student export and permanently delete all of their data.
  • Retain tasks for a defined period rather than keeping them forever.
  • Explain in plain language what is collected, why, and for how long.
